申请内测

申请按顺序处理，小批量放号。目前还没有自助注册流程——比起发给你一个坏掉的链接，我们更愿意直说。

在 GitHub 上提交申请
  • 你用的是哪个 Coding Agent（Codex / Claude Code / Cursor / 自研）
  • 项目大致类型，以及你最想守住的那条行为
  • 打算只在本地跑，还是以后也想接 CI
打开申请表单 我们存什么

表单会以公开 issue 的形式打开，方便你自己回头查记录。请不要在里面贴源码、密钥或客户数据。

这轮内测在验证什么

验证引擎现在已经能跑，外围的自动化还在建。下面把状态拆开写，让你清楚自己要试的到底是什么；列出的一切都不作为交付承诺。

引擎里已经可用

  • 本地真实 Chromium 会话里执行确定性检查
  • PASS / FAIL / UNKNOWN 三态，UNKNOWN 绝不会被算作通过
  • 绑定代码版本的证据，以及单文件 HTML 报告
  • 人工批准闸门：没有已批准预期，就不执行
  • 单项目、单次运行单场景，工作台只绑本地回环地址

正在验证，尚未交付

  • 由 Coding Agent 改动后 Hook 自动触发一次验证
  • 供 CI 调用的全量回归 CLI 命令，以及可跑的 CI 示例
  • 定时回归，以及能区分触发源的运行记录
  • 自带模型 Key 前提下的检查步骤辅助起草

规划中，不承诺时间

  • 共享预期库与团队审批留痕
  • 托管 Runner、多环境矩阵、SSO
  • 内置调度与自动失败修复

我们绝不索取什么

  • 你的源码或仓库 Token
  • 你的模型 API Key——这一页不会要，邮件里也不会要
  • 生产环境凭据、客户数据，以及任何你不愿意公开的内容

为什么走 GitHub

静态站没法诚实地承诺「安全地替你保存邮箱」，而一个会静默失败的收集表单比没有表单更糟。公开 issue 不需要后端，留得下可回溯的记录，追问也能在同一个地方继续。如果你的组织用不了 GitHub，在任何一条 issue 下回复，我们换别的渠道。
