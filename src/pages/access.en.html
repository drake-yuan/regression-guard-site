What we're validating in early access

The verification engine runs today; the automation around it is still being built. Here is the split, so it is clear what you would actually be testing. Nothing below is a delivery commitment.

Available in the engine today

  • Deterministic checks executed locally in a real Chromium session
  • PASS / FAIL / UNKNOWN, where UNKNOWN is never reported as a pass
  • Evidence and a single-file HTML report bound to a code version
  • A human approval gate: no run against an unapproved expectation
  • One project, one scenario per run, on a loopback-only local workbench

Being validated — not shipped

  • Coding-agent hooks that trigger a run after a change
  • A CLI command for full regression, plus a working CI example
  • Scheduled runs and records that distinguish the trigger source
  • Model-assisted check drafting behind a bring-your-own-key option

Planned — no date promised

  • Shared expectation libraries and team approval trails
  • Hosted runners, multi-environment matrices, SSO
  • Built-in scheduling and automatic failure repair

What we never ask for

  • Your source code or a repo token
  • Your model API key, on this site or by email
  • Production credentials, customer records or anything you would not post publicly

Why the request goes through GitHub

A static site cannot honestly promise to store your email securely, and a form that silently fails is worse than no form. A public issue needs no backend, keeps a record you can point to, and lets us ask follow-up questions in the same place. If your organisation cannot use GitHub, reply on any issue thread and we will find another channel.
